# Background transfer progress — 0.4.0

Android's foreground service owns the local hotspot, pinned HTTPS server and receiver. Home or closing the Activity detaches its interface without stopping the session. An ongoing low-priority notification shows sending/receiving progress and provides Open and Stop sharing. The notification never includes pairing secrets or filenames; its public Lock Screen version is generic. Android 13+ asks for notification permission. If denied, Android can hide progress from the notification drawer; use Nearby to stop the service or change notification permission in Settings.

The service starts only from a user action in the foreground, uses the connectedDevice type, never auto-starts at boot, and does not automatically restart an authorized session after process death. Stop closes sockets, invalidates pairing, closes the hotspot and releases Wi-Fi/CPU locks. Android/Samsung may still stop a process or network; saved file selections and iPhone checkpoints remain the recovery path. A sender's progress counts bytes read for socket delivery; only the receiving iPhone can confirm its final verified save.

On iOS 26+, Nearby requests a `BGContinuedProcessingTask` when the user starts or resumes a transfer. When Apple grants execution, its system Live Activity provides progress on supported Lock Screen/Dynamic Island surfaces and a cancel control. It uses the existing local-only pinned HTTPS connection and needs no push server or internet service. Background progress has a separate final verification stage; the task is marked successful only after a full received-file hash or Android's verified upload acknowledgement.

Nearby requests immediate execution with a fail strategy, so no transfer is queued to start unexpectedly later. Keep Nearby open until it says background transfer is enabled. If the request is unavailable/declined, iPhone downloads pause when leaving Nearby; uploads stop and require a new send. On system cancellation/expiry, interrupted downloads keep committed pieces. Uploads still have no resume support: check Android before resending if acknowledgement was lost. Force-quitting either app is not a supported way to keep a transfer running.

The iPhone's private checkpoint files and outgoing snapshots remain encrypted with device storage protection and are accessible after first unlock so a permitted transfer can continue while subsequently locked. No network/certificate/pairing validation is bypassed. Free SideStore installation still uses Camera/Settings Wi-Fi joining. The permitted task prefix covers ordinary suffixes added to the source bundle identifier; other re-signing changes can disable background scheduling, in which case the app shows a foreground fallback.

This uses Apple's system progress interface, not a custom WidgetKit Live Activity design. Full native Nearby/Files/Activity tabs and the original demo layouts remain a release requirement. Apple's scheduling, actual lock-screen presentation, SideStore's installed identifier/profile and Samsung background behavior need physical device testing; simulator transition tests cannot establish those results.

Implementation references: [Android connected-device foreground services](https://developer.android.com/develop/background-work/services/fgs/service-types#connected-device), [Apple continued processing and system progress](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados), [dynamic registration explained by Apple](https://developer.apple.com/videos/play/wwdc2025/227/).
